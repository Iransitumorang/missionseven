02 / Docker Compose Core Engine

Definisi & Problem Solving

Docker Compose adalah alat manajemen untuk mengonfigurasi dan menjalankan aplikasi multi-container berbasis Docker menggunakan satu file definisi tunggal. Mengeliminasi proses manual eksekusi runtime terpisah.

Skenario Tradisional

Tanpa Compose, operasional kluster mewajibkan eksekusi docker run berkali-kali secara manual, setup network bridge terisolasi, serta mounting volume satu per satu yang rentan terjadi kesalahan konfigurasi.

Skenario Praktis (Compose)

Seluruh spesifikasi infrastruktur dideklarasikan secara terpusat dalam berkas docker-compose.yml. Cukup satu instruksi command untuk mengendalikan seluruh siklus hidup service.

03 / Struktur File docker-compose.yml

services: frontend: build: ./frontend # Path direktori Dockerfile ports: - "3000:3000" volumes: - ./frontend:/app # Live reload depends_on: - backend backend: build: ./backend ports: - "5000:5000" environment: - DB_HOST=db # Service name jadi hostname - DB_PORT=5432 depends_on: - db
db: image: postgres:15 environment: - POSTGRES_USER=iran - POSTGRES_PASSWORD=secret - POSTGRES_DB=videobelajar volumes: - pgdata:/var/lib/postgresql/data volumes: pgdata: # Deklarasi named volume

05 / Multi-Container Networking & Data Persistence

Isolated Bridge Networking

Secara default, seluruh service di dalam satu berkas Compose otomatis terhubung ke satu default network internal yang sama.

Setiap container bisa saling berkomunikasi cukup menggunakan Nama Service sebagai hostname (contoh: jdbc:postgresql://db:5432/). Docker mengelola internal DNS resolusinya.

Data Persistence (Volumes)

Secara default, container bersifat ephemeral (sementara). Jika container mati atau di-recreate, data di dalamnya hilang.

Menggunakan Named Volumes mengekstrak penyimpanan keluar dari filesystem container ke host filesystem, sehingga data tetap aman saat container restart.

06 / Arsitektur Kubernetes (K8s) Cluster

Kubernetes adalah sistem declarative configuration untuk mengotomatisasi penyebaran, penskalaan, dan pengelolaan kontainer.

Master Node (Control Plane)

Otak logis kluster yang bertugas memantau kondisi dan merespons perubahan:

  • ├── API Server (Gerbang utama REST)
  • ├── Scheduler (Penentu lokasi pod)
  • └── Controller (Pengelola state kluster)

Worker Node (Execution Plane)

Node runtime tempat container berjalan dalam isolasi terkontrol:

  • ├── Pod (Unit abstraksi terkecil K8s)
  • ├── Pod
  • └── Pod

07 / Pemetaan Abstraksi Topologi K8s

Pemetaan hierarki struktural komponen Kubernetes dalam tata kelola lingkungan produksi:

Cluster

= Satu Kota

Kesatuan ekosistem infrastruktur fisik atau virtual yang dikelola secara terpusat.

Node

= Rumah-Rumah di Kota

Mesin host individual (Server) penyedia resource komputasi di dalam kluster.

Pod

= Kamar di Rumah

Unit runtime terkecil tempat container (penghuni) dialokasikan dan berjalan.

08 / Core Objek K8s: Pod & Deployment

Pod: Unit Terkecil

Pod membungkus satu atau beberapa container aplikasi. Kontainer dalam satu Pod berbagi network IP, storage space, dan port range yang sama.

Umumnya diimplementasikan dengan rasio: 1 Pod = 1 Container.

Deployment: Pengendali Pod

Deployment berperan sebagai manajer/blueprint deklaratif. Developer mendikte jumlah replika Pod yang harus aktif (misal: 3 replika).

Jika ada Pod crash atau mati, Deployment otomatis mendeteksi dan melahirkan Pod pengganti baru untuk menjaga ketersediaan.

09 / Contoh File Deployment (deployment.yaml)

apiVersion: apps/v1 kind: Deployment metadata: name: nginx-test spec: replicas: 3 # Menjaga 3 pod tetap hidup selector: matchLabels: app: nginx template: metadata: labels: app: nginx spec: containers: - name: nginx-container image: nginx:1.27 ports: - containerPort: 80

10 / Akses Jaringan Statis: Service Engine

Problem Alamat IP Dinamis Pod

IP internal Pod selalu berubah setiap kali pod dihancurkan, crash, atau dibuat ulang oleh deployment. Hal ini menyulitkan sistem luar untuk melakukan interkoneksi endpoint secara konsisten.

Solusi Komponen Service

Service bertindak sebagai pintu gerbang statis bergaransi IP dan nama DNS tetap. Ia memetakan traffic menuju sekelompok Pod target secara dinamis sekaligus bertindak sebagai internal Load Balancer kluster.

Ekspose Jaringan Manual CLI

kubectl expose deployment nginx-test \ --port=80 \ --target-port=80 \ --type=ClusterIP

11 / Abstraksi Konfigurasi: ConfigMap & Secret

Tujuan Utama Separasi Konfigurasi

Mengamankan sistem dengan cara memisahkan berkas variabel lingkungan (ENV) dari source code aplikasi, memastikan tidak ada parameter sensitif atau hardcoded data di repositori git.

ConfigMap (Data Umum)

Tempat menyimpan key-value data non-sensitif (seperti alamat API eksternal, nama aplikasi, atau port runtime).

kind: ConfigMap data: APP_NAME: "Monitoring"

Secret (Data Sensitif)

Tempat khusus menampung credential sensitif (seperti password DB, token OAuth, API Key) yang terenkapsulasi encoding Base64.

kind: Secret data: password: MTIzNDU= # 12345

13 / Prosedur Inspeksi & Analisis Log Pod

Debugging & Observability

Aktivitas utama pengembang dalam melacak bug, runtime error, atau anomali aplikasi dilakukan dengan memonitor aliran stdout/stderr kontainer via CLI.

Standard Logs & Realtime Streaming

Membaca rekaman log statis:

kubectl logs [nama-pod]

Melakukan tailing/streaming log secara realtime:

kubectl logs -f [nama-pod]

Skenario Kasus Khusus

Membaca log dari pod yang mengalami crash-loop / restart otomatis (membaca state log sebelumnya):

kubectl logs [pod] --previous

Spesifik log jika pod membawa multi-container:

kubectl logs [pod] -c [container-name]

14 / Up-Down Deploy (Horizontal Scaling)

Elastisitas Resource Alokasi

Mengatur kapasitas penampungan traffic secara dinamis dengan menambah atau mengurangi kuantitas replika Pod aktif tanpa memicu downtime sistem.

Sintaks Manual Scale Up / Down

Menaikkan populasi pod menjadi 5 instance saat beban puncak kerja tinggi:

kubectl scale deployment frontend --replicas=5

Menurunkan populasi pod menjadi 2 instance untuk menghemat resources:

kubectl scale deployment frontend --replicas=2

Dampak Internal Kluster

Kube-Scheduler secara cerdas langsung mengalkulasi sisa kapasitas node server, lalu menginstruksikan container runtime membuat kontainer baru atau mematikan kontainer lama secara instan.

15 / Zero-Downtime Deployment: Rolling Update

Strategi Pemutakhiran Aplikasi Tanpa Interupsi

Kubernetes memperbarui aplikasi ke versi image terbaru secara bertahap. Pod versi lama dimatikan satu per satu hanya setelah Pod versi baru dipastikan siap menerima traffic.

Pipeline Perintah Eksekusi

Menyuntikkan image versi teranyar:

kubectl set image deployment/frontend frontend=nginx:1.27

Memantau transisi deployment:

kubectl rollout status deployment frontend

Emergency Rollback

Jika image baru bermasalah di production, eksekusi perintah pembatalan instan berikut untuk mengembalikan kluster ke versi stabil sebelumnya:

kubectl rollout undo deployment frontend

16 / Isolasi Lingkungan via Namespace

Definisi Virtual Cluster

Namespace berfungsi memisahkan satu kluster fisik menjadi beberapa wilayah logical terisolasi. una untuk memisahkan siklus kerja development tanpa risiko tabrakan resource konfigurasi.

Segmentasi Standar Environment

  • ├── default (Default namespace)
  • ├── dev (Development area)
  • ├── uat (User Acceptance Testing)
  • └── prod (Production stable)

Contoh Manajemen Konteks CLI

Menerapkan file manifest ke target wilayah khusus:

kubectl apply -f deploy.yaml -n dev

Melihat pod yang terisolasi di area dev:

kubectl get pods -n dev

17 / CI/CD & Automation Pipelines

Otomatisasi Modern Alur Kerja DevOps

Mengeliminasi intervensi manual developer di server lokal. Seluruh proses pengujian, kompilasi, distribusi artifak, hingga pemutakhiran server diserahkan sepenuhnya ke sistem robotik pipeline.

Arsitektur Alur Kerja Integrasi

  1. Developer melakukan Push Code ke GitHub.
  2. GitHub Actions Workflow terpicu otomatis.
  3. Sistem merakit Docker Build & menguji kode.
  4. Artifact dikirim ke Docker Hub Registry.
  5. Perintah dikirim ke K8s API untuk trigger update.

Manfaat Pipeline

  • Reproducible: Hasil rilis seragam dan konsisten.
  • Safe: Pengecekan standar keamanan terotomatisasi.
  • Fast: Pengiriman fitur baru ke user dalam hitungan menit tanpa mengganggu jalannya aplikasi aktif.
